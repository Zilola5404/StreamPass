# StreamPass — Конституция проекта

> Версия: 1.0 | Дата: 2026-08-03 | Статус: Актуально

## 1. Назначение документа

Этот документ — единый свод правил для всех участников разработки (людей и AI-агентов). Любое изменение в репозитории должно соответствовать этим правилам.

---

## 2. Главные правила разработки

1. **Не ломать существующие функции.** Перед изменением изучить текущее поведение через код и тесты.
2. **Clean Architecture.** Слои: `domain` → `application` → `infrastructure` → `http`. Бизнес-логика только в `application` и `domain`.
3. **Dependency Injection через конструкторы.** Composition root — `backend/cmd/server/main.go`.
4. **Минимальные зависимости.** Предпочитать stdlib и dependency-free реализации (JWT, Redis, YAML) там, где это оправдано.
5. **Один commit = одна задача.** Атомарные, обратимые изменения.
6. **Не выполнять две большие задачи одновременно.**
7. **При сомнениях — не менять код.** Зафиксировать вопрос в `ai/OpenQuestions.md`.

---

## 3. Правила работы AI

1. **Перед любой задачей прочитать:**
   - `docs/00_ProjectRules.md` (этот файл)
   - `docs/14_AIContext.md`
   - `docs/03_CurrentState.md`
   - `docs/04_Backlog.md`
   - `ai/CurrentTask.md`, `ai/CurrentFocus.md`
2. **Не придумывать данные.** Если информации нет — писать `TODO: Требуется уточнение` или `Не реализовано`.
3. **Не создавать ложную архитектуру.** Документировать только то, что есть в коде.
4. **Не менять код без явной задачи.** Задачи на документацию — только документация.
5. **После изменений обновить:**
   - `docs/10_Progress.md`
   - `ai/LastSession.md`
   - Соответствующие docs при изменении архитектуры/API/БД
6. **Smoke test после каждого этапа:** `go build ./...`, `go test ./...`, при изменении клиента — `flutter test`.

---

## 4. Правила изменения архитектуры

1. Любое архитектурное решение фиксировать в `docs/11_Decisions.md` (ADR).
2. Обновить `docs/07_Architecture.md` при изменении компонентов или взаимодействий.
3. Не вводить микросервисы без ADR — MVP = Go monolith (см. ТЗ §11).
4. Новые внешние зависимости — только через ADR с обоснованием.
5. API-изменения — только с версионированием `/api/v1/...`.

---

## 5. Правила коммитов

- Сообщения на русском или английском, осмысленные (как в git history).
- Один commit = одна логическая задача.
- Не коммитить: `.env`, секреты, build artifacts, `streampasscore.aar`.
- Не коммитить без явного запроса пользователя (для AI-агентов).

---

## 6. Правила документации

1. Документация отражает **реальное** состояние кода, не планы.
2. Планы и backlog — в `docs/04_Backlog.md`, `docs/20_Roadmap.md`.
3. Спецификация продукта — `docs/02_TZ.md`.
4. AI-контекст — `docs/14_AIContext.md` (обязательно поддерживать актуальным).
5. После каждого значимого изменения обновлять `docs/17_CHANGELOG.md`.

---

## 7. Требования качества кода

| Область | Требование |
|---------|------------|
| Go | `go vet ./...` без замечаний; `go build ./...` успешен |
| Dart/Flutter | `flutter analyze` без ошибок; следовать `flutter_lints` |
| Тесты | Новая бизнес-логика — unit-тесты; критичные пути — integration |
| Ошибки | Единый формат через `shared/errors` и `httpx.WriteError` |
| Безопасность | Argon2id для паролей; JWT HS256; rate limiting на публичных endpoint |
| Логирование | Структурированный JSON; без PII и URL в telemetry |

---

## 8. Запреты

- ❌ Хранить секреты в коде или `config.yaml` (только `${ENV}`)
- ❌ Собирать URL/историю сайтов в telemetry
- ❌ Ломать обратную совместимость API без версионирования
- ❌ Добавлять Kubernetes, ML, собственный транспорт в MVP (см. ТЗ §21)
- ❌ Обещать «ускорение интернета» — только «стабильный маршрут»

## 10. Definition of Done (кратко)

Полный чеклист — `docs/15_DefinitionOfDone.md`.

- Тесты проходят (где применимо)
- Документация обновлена

- Нет регрессий существующих функций
