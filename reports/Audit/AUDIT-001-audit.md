## 1. Несоответствия ТЗ (Требованиям к функционалу)

1. **Отсутствие математической проверки CIDR подсетей (Critical / Major):**
   - В `server.ts` объявлены массивы `directCidrs` (например, `178.248.232.0/21`) и `relayCidrs` (`142.250.0.0/15`).
   - Однако в обработчике `POST /api/rules/test-route` подсети полностью игнорируются при тестировании IP-адресов. Проверяются только строковые домены через `.endsWith()` и `.includes()`. Запросы с целевыми IP не сопоставляются с CIDR масками.
2. **Симуляция TUN/eBPF и Hysteria2 бинарного протокола (Info / Architecture Note):**
   - Протокол Hysteria2, ротация портов (UDP 443 → TCP 443) и DoQ рендерятся на уровне высокоуровневой логики Express API и React UI. Входной трафик не проксируется через настоящий системный TUN-интерфейс или QUIC-сокет (что допустимо для веб-демо/панели управления, но требует явной фиксации в документации).
3. **Отсутствие фоновой очистки и валидации срока действия подписок (Minor):**
   - Срок действия подписки (`activeUntil`) передается в ответах API, но backend не содержит фонового таска (cron/interval) для автоматического разжалования тарифа с `PRO`/`MAX` до `FREE` при наступлении даты истечения.

## 2. Архитектурные замечания

1. **Хранение состояния в оперативной памяти процесса (In-memory State) — P0:**
   - Данные пользователей (`users`), сессии (`activeSessions`), реле-серверы (`relays`), правила (`currentRuleSet`), пользовательские исключения (`userExclusions`) и история платежей (`paymentsHistory`) хранятся в обычных JS-массивах в `server.ts`.
   - При любом перезапуске контейнера/процесса все созданные аккаунты, оплаченные подписки и пользовательские правила сбрасываются.
   - Делает невозможным горизонтальное масштабирование (Horizontal Pod Autoscaling / Multi-instance deployment), так как балансировщик нагрузок будет направлять запросы на разные инстансы с рассинхронизированным состоянием.
2. **Лишние и неиспользуемые зависимости (Minor):**
   - В `package.json` подключены пакеты `@google/genai` и `dotenv`, которые фактически не импортируются и не используются ни в `server.ts`, ни в компонентах `src/`.
3. **Отсутствие сервисного слоя на бэкенде (Minor):**
   - Вся логика авторизации, маршрутизации, симуляции эндпоинтов YooKassa и биллинга сосредоточена в одном монолитном файле `server.ts` (620 строк) без разделения на контроллеры, сервисы и репозитории.

## 3. Замечания по безопасности

1. **Хранение паролей в открытом виде (Critical — P0):**
   - В `server.ts` (строки 218-224) поле `passwordHash` заполняется открытым текстом (`passwordHash: password`). Хеширование (bcrypt/argon2) отсутствует.
2. **Использование фиктивных JWT-токенов без подписи (Critical — P0):**
   - Токены авторизации генерируются путем конкатенации строк: ``jwt_token_${newUser.id}_${Date.now()}``.
   - Токен не подписывается секретным ключом (HMAC/RSA), не содержит требований стандарта RFC 7519, а проверяется по прямому вхождению в объект `activeSessions`.Любой злоумышленник с подбором ID может подделать токен.
3. **Зашитые в код секретные ключи администрирования (Critical — P0):**
   - В `POST /api/admin/rules` и `POST /api/admin/servers` проверка доступа осуществляется сравнением заголовка `X-Admin-Key` с жестко зашитыми константами: `adminKey !== "admin-secret-key" && adminKey !== "demo-admin"`.
   - Ключи администрирования открыто присутствуют в исходном коде.
4. **Отсутствие валидации и санитизации входных данных (Major):**
   - Эндпоинты добавления правил (`/api/rules/exclusions`) и серверов (`/api/admin/servers`) не валидируют формат доменных имен, IPv4/IPv6 адресов, допуская сохранение синтаксически некорректных или вредоносных строк.

## 4. Замечания по производительности

1. **Утечка памяти в хранилище сессий и логов (Major):**
   - Объект `activeSessions` пополняется при каждом входе или регистрации, но не имеет механизма удаление устаревших сессий после истечения `expiresAt`.
   - При длительной работе сервера объем памяти под сессии и историю платежей будет неограниченно расти.
2. **Линейный поиск в Decision Engine — $O(N)$ (Minor):**
   - В `/api/rules/test-route` поиск по массивам `directDomains`, `relayDomains` и `fallbackDomains` осуществляется через итеративный цикл `for...of`. При росте списков правил до десятков тысяч доменов это вызовет задержки обработчика Express.
3. **Отсутствие мемоизации вычислений на фронтенде (Minor):**
   - В компонентах `Diagnostics.tsx` и `RouteTester.tsx` тяжелые операции агрегации статистики выполнются при каждом перерендере без `useMemo`.

---

## 5. Замечания по качеству кода

1. **Дублирование демо-пользователя по умолчанию (Minor):**
   - В `GET /api/auth/me` при отсутствии валидного токена возвращаются данные демо-пользователя `usr-demo`. Это создает неявное поведение, при котором неавторизованный клиент выглядит как вошедший пользователь.
2. **Отсутствие строгой типизации эндпоинтов Express (Minor):**
   - Параметры `req.body` и `req.params` в `server.ts` кастятся вручную без использования схем валидации (например, Zod / Yup / TypeBox).

---

## 6. Замечания по масштабируемости

1. **Невозможность работы в stateless-режиме:**
   - Текущая реализация привязана к single-process архитектуре.
2. **Отсутствие версионирования API:**
   - Пути эндпоинтов начинаются с `/api/...` вместо `/api/v1/...`, что затруднит проведение обратной совместимости при обновлении мобильных и десктопных клиентов.

---

## 7. Состояние документации

1. Файлы документации (`docs/`) были актуализированы для монолитной структуры, однако спецификации API не содержали явного предупреждения о демонстрационном характере хранения токенов и зашитых Admin-ключей.

## Рекомендации

### Приоритет P0 (Блокирующие релиз / Критические)
1. **Безопасность авторизации:**
   - Внедрить библиотеку `jsonwebtoken` для генерации честных signed JWT.
   - Заменить хранение открытых паролей на хеширование с использованием `bcrypt` / `argon2`.
2. **Безопасность Admin API:**
   - Вынести `X-Admin-Key` в переменные окружения (`process.env.ADMIN_SECRET_KEY`) и удалить зашитые строки из `server.ts`.
3. **Персистентность данных:**
   - Подключить СУБД (PostgreSQL / SQLite / Firestore) вместо вложенных JS-массивов для сохранения пользователей, сессий, подписок и правил.

### Приоритет P1 (Высокий)
1. **Decision Engine & CIDR Math:**
   - Реализовать парсинг и проверку масок CIDR (`ip-range-check` или чистая битовая математика) в эндпоинте `/api/rules/test-route`.
2. **Очистка памяти:**
   - Добавить периодический cron-таск для очистки просроченных сессий в `activeSessions`.
3. **Валидация входящих данных:**
   - Внедрить Zod-схемы для валидации тела запросов во всех POST/PUT эндпоинтах.

### Приоритет P2 (Средний / Оптимизация)
1. **Оптимизация сопоставления доменов:**
   - Перевести списки правил `directDomains` и `relayDomains` на структуру Prefix Tree (Trie) или Set для $O(1)$ / $O(K)$ поиска.
2. **Чистка зависимостей:**
   - Удалить неиспользуемые пакеты из `package.json`.
3. **Версионирование API:**
   - Добавить префикс `/api/v1` для всех эндпоинтов.
